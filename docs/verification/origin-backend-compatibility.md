# Baseline client requests against the Draft backend

This local acceptance exercises the original published `0.2.10` server caller and transport against registered candidate Convex functions. It verifies seven cases through 34 real loopback HTTP requests, including four intentional rejections. The [detail report](evidence/origin-backend-compatibility-031/backend-compatibility-report-031.json), [observed requests and states](evidence/origin-backend-compatibility-031/observations.json), [loaded module identities](evidence/origin-backend-compatibility-031/module-loads.json), [check output](evidence/origin-backend-compatibility-031/checks.log), and [hash manifest](evidence/origin-backend-compatibility-031/manifest.json) preserve the evidence.

The baseline is `0eb372a94715527931043a1b6d8c02a50194dbb0`. Its untouched `server/origin-cloud.ts` exports `runOriginTool` and `convexOriginClient`; they execute at their original module IDs in a separate detached reference checkout. The new caller is bound to observed integration source `dd5b63ef914c5a546ea99cbef65b29b33078c7e9`. The registered backend runs source `3b85cb69c0c907a9aa08ba98b664cb5889cbe83a`; its 26 loaded modules and all nine reviewed Draft implementation blobs match that observed integration. The loader binds 209 original source modules and their Git blobs and normalized SHA256 values. The client SDK is Convex `1.47.0`, matching the baseline lockfile; the backend uses its pinned `1.45.0`, with `convex-test 0.0.60` and Vitest `5.0.2` on Node `24.21.0`.

The adapter listens on an OS-selected port bound to `127.0.0.1`. The real baseline `ConvexHttpClient` serializes query and mutation requests using the Convex HTTP protocol. The adapter decodes that protocol and invokes the actual registered candidate queries/mutations, argument validators and return validators through `convex-test`. Query responses and task writes come from those functions and disposable synthetic documents. Task creation and authorization responses are not mocked. The internal repair phases execute as registered mutations directly through the same isolated Convex fixture.

| Required coverage | Observed behavior |
| --- | --- |
| Existing explicit lanes | The actual old caller sends an explicit Todo column; the actual backend stores Todo unchanged. |
| Explicit new Draft | The old caller explicitly chooses Draft and the new backend retains that exact column ID and `done:false`. |
| Omitted destination | The actual new caller omits `columnId`; the backend supplies Draft. A direct request through the untouched old transport also preserves omission and resolves to Draft. |
| Transitional legacy Idea privacy | Small Idea-only, deep Idea-only and deep unflagged-Draft fixtures are checked before repair and after every phase. Ambiguous deep boards remain held; the final deep Draft wins over Idea, while Idea-only boards adopt their Idea in place. |
| Existing task/link preservation | All six existing task documents, their three embedded GitHub issue links, and three `taskPullRequests` link rows serialize to identical bytes before and after the ordered repair. |
| Viewer and foreign-workspace denial | Requests through the old real transport reach registered backend guards. A project viewer can read its board but cannot write; a foreign member and a foreign column ID also reject, with task rows unchanged. |

The actual `columns`, `legacyIdeas`, and `projects` internal phases require three, three and two pages respectively. Every actual receipt passes the canonical bounded receipt parser. After all phases complete, the actual old default-creation caller queries each of the three legacy boards, sees semantic Draft first and creates there. A separate invalid-priority request proves the registered argument validator rejects incompatible protocol input.

## Release boundary

This is evidence of the specified old-client request contracts against registered candidate handler logic. It does not claim a hosted Convex deployment, the full old React app, a real browser, a packaged desktop client, GitHub mirroring, mail delivery or production acceptance.

`releaseSource` remains `null`. Before authorizing the compatibility gate, the integration owner must compare every loaded candidate-client/backend source blob and digest, plus all nine reviewed Draft implementation files, with the actual final frozen release. CI, native packages, private release assets, site preflight and all subsequent real deployment/repair/cleanup/mail/publication gates remain separate requirements. Old default creation is verified after all three ordered phases; this report does not authorize publishing clients before that repair completes.

The detail report's private copy is `.omb-scratch/backend-compatibility-report-031.json`. The root-owned authorization summary is the separate `.omb-scratch/backend-compatibility-031.json`; its `reportSha256` hashes the detail report, never itself. This worker creates no authorization summary, release inputs, delivery state or completed backend receipt.
