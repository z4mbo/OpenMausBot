This bounded review compares actual source changes from twenty merged OpenMausBot PRs with Origin. Three have adopted functionality, counting #2947's narrow permission adaptation; seventeen remain deferred or have no applicable product patch. The final eight comparisons used official merge patches and blob hashes against Origin source `43c7fd9ae4316647a2d7705745b32812635c56cb`; their dispositions are recorded below. Metadata discovery does not count as completed review. A merge upstream is an input to review, not permission to replace Origin's account, project, approval or release contracts. Origin 0.2.7 is published from frozen source `dbdac25fcd014d231e694aa8665d326b235af616` (`origin-v0.2.7`); public delivery is verified in the [delivery record](origin-delivery.md) and [verified 0.2.7 delivery evidence](evidence/origin-delivery-027/report.json). Further merges belong to the daily review at 06:00 Europe/Rome.

## Adopted changes

### HTTP MCP failure messages

[OpenMausBot #3026](https://github.com/milind-soni/OpenMausBot/pull/3026), merge [`431dba374372536c7a527981cc62e9ac8a3e19b7`](https://github.com/milind-soni/OpenMausBot/commit/431dba374372536c7a527981cc62e9ac8a3e19b7), is adapted in Origin commit `e25f6633c`. The proxy preserves the HTTP status and gives a bounded recovery hint without disclosing credentials or a provider's raw response body. Six regression tests failed before the adaptation. This review found the adaptation already present and did not apply it again.

### Paired-device appearance saves and host validation

[OpenMausBot #2988](https://github.com/milind-soni/OpenMausBot/pull/2988), merge [`5ea9455ee82bab81cce5cd517046cce581a53c67`](https://github.com/milind-soni/OpenMausBot/commit/5ea9455ee82bab81cce5cd517046cce581a53c67), is adapted in Origin commit `1b9bfbf5f`. Origin keeps its own project/account hierarchy and existing server authentication.

Two concrete defects were reproduced:

| Severity | Input and state | Before | Fix |
|---|---|---|---|
| P2 | Authenticated paired phone sends the avatar panel's `PATCH /api/bots/:id` colour, mascot, reset or framing payload. | The companion returns `404 no route`, so changes cannot be saved. | Allow only the exact bot PATCH route; apply the client display-field allowlist even when the proxy reaches the host as a loopback caller. Protected fields mixed with a colour edit fail before any write. |
| P3 | Host sends `{ "unread": true, "color": "#168aad" }`, or a non-boolean pin / invalid expression. | The real server returns 200 and stores values outside its `MausColor` / boolean / string wire contract. For example, an array pin is truthy, so malformed input can pin the bot. | Share the ten palette names in the wire contract and validate colour, pin and expression before constructing or applying the patch. Existing avatar/profile validators remain in effect. |

The adaptation adds the five avatar fields already accepted by the profile route: `avatarUrl`, `avatarCrop`, `avatarZoom`, `avatarFocusX`, `avatarFocusY`. Stored-image checks and crop/range validators still run. It does not grant a paired client permission to change models, instructions, computer access, hierarchy or approvals. The proxy overwrites a forged companion marker; a caller cannot obtain host authority by sending `x-openmausbot-companion: 0`.

The shared palette is exported by `shared/wire.ts` and re-exported by `src/lib/mascot.ts`, so API validation and renderer choices use the same names. Companion documentation records the exact expanded route.

Origin already handles custom hexadecimal colours defensively in `botPalette`; the upstream description's bubble crash does not reproduce here and is not claimed as an Origin bug. Origin's custom Liquid/Zap colour picker persists through the separate `avatar-look` route, which remains unchanged and keeps custom hex support.

### Live browser view permission revocation (partial adoption)

[OpenMausBot #2947](https://github.com/milind-soni/OpenMausBot/pull/2947), “Browser panel v2: the page fills the panel, sharp, over T3 Code's stream,” merge [`62a7b7ac72e4f0adae1b373032592df7327d7b26`](https://github.com/milind-soni/OpenMausBot/commit/62a7b7ac72e4f0adae1b373032592df7327d7b26), prompted a narrow permission adaptation in Origin commit `9c1510a03`.

The concrete P1 scenario is an authorized member opening a bot's live browser, followed by that bot becoming invisible to the member while the member and browser sessions remain live. Origin's old view predicate still returns true, so the production `BrowserLive` class can forward another private frame. A visibility change before initialization completes is also incorrectly accepted. `server/host/browser-view-access.ts` now includes current bot visibility in its predicate; `BrowserLive.recheckViewers` and the `audienceChanged` hook close revoked viewers immediately, including streams waiting for their next frame, while retaining another viewer's valid access.

The original real predicate fails two permission tests. The production streaming class with synthetic transport/frame input also retains the second frame before correction. Afterward, focused access/browser tests pass 114 cases with 12 existing Windows/OS skips; server TypeScript and size/legacy guards pass. The standard isolated route fixture covers startup, doctor, seed, auth/CSRF checks and missing-engine 503 handling. It does not prove a successful real browser stream being revoked through HTTP. Synthetic class/transport proof and route-fixture coverage are distinct acceptance boundaries.

The complete BrowserPanel v2 is deferred. Its upstream ChromeEngine/BrowserService tree is absent from this Origin base, so copying the panel or streaming surface alone would call missing lifecycle and permission services. The page-filling stream, viewport/zoom, popups and other full-panel behavior are not claimed as imported or verified. This PR is counted once as partially adopted, not as an additional deferred review.

## Paired-appearance verification

Run from the isolated worktree:

```powershell
pnpm.cmd exec vitest run companion/test server/request-auth.test.ts server/bot-profile.test.ts src/lib/mascot.test.ts src/lib/user-bubble-tone.test.ts
node --experimental-strip-types scripts/verify-paired-appearance.ts
pnpm.cmd exec tsc -b
pnpm.cmd exec tsc -p tsconfig.server.json
```

Before applying product changes, the paired-route/field tests had 9 failures. A separate host request test failed because the invalid colour returned HTTP 200 instead of 400. Their retained logs are [paired-route failures](evidence/origin-upstream/paired-before.log) and [host validation failure](evidence/origin-upstream/host-before.log).

After the adaptation, the focused suite above passed 556 tests across 25 files, with 3 existing skipped tests. Both TypeScript builds and focused `oxlint --deny-warnings` passed. The added request-auth cases check every allowed display field independently and reject protected fields when mixed into a display edit.

The real-server recipe uses `launchVerificationServer` from the shared control surface, creates a real companion proxy against that exact temporary server, and uses only a synthetic paired token. It verifies successful saves read from the host, refusal without partial writes, marker spoofing, bad values, missing/wrong credentials, and a normal fake-engine conversation driven through mapped `send`, `wait`, `messages` commands. Its [JSON evidence](evidence/origin-upstream/paired-appearance.json) includes requests, resulting statuses, settled state, transcript and persistent server-log path. The script closes only its own proxy/server and removes the fixture's temporary data.

The checks establish HTTP behavior and a fake-engine turn. They do not establish a physical phone's native avatar controls, real provider behavior, macOS/Windows packaged acceptance or public deployment. Origin's separate UI and delivery records cover their own tested boundaries.
