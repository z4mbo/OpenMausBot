## Windows shard 4: concrete test-fixture false positive

The [completed Windows shard log](evidence/origin-candidate-054/ci/windows-shard4-complete.log) identifies one failing assertion in `server/drivers/openai-chat-tools.test.ts:864`: the entire serialized event stream must not contain the synthetic four-character credential `abab`. The credential was correctly redacted from the actual assistant content: the combined deltas and completed text both read `Before [redacted] after.` The forbidden substring instead appeared in a randomly generated thread UUID, `12ec893a-d364-4ba8-abab-8f537e12e310`. The failure therefore establishes a test-fixture collision, not an observed credential leak or application regression.

That shard records 1 failed, 4,836 passed and 124 skipped tests; its file summary is 1 failed, 368 passed and 17 skipped, for 386 files. The [deterministic RED](evidence/origin-candidate-054/local/credential-canary-red.log) fixes the thread ID to that UUID and reproduces both one-chunk and split-chunk false positives: 2 failed, 104 other cases filtered/skipped, while the actual content remains redacted. The correction keeps that fixed UUID, uses the non-UUID prefix `fixture-key|` repeated twice as the overlapping synthetic credential, and retains the whole-event serialization and redacted-output assertions. It additionally checks that the thread identity is preserved. The [complete touched file](evidence/origin-candidate-054/local/credential-canary-green.log) then passed all 106 cases in 18.25 seconds. This is focused local correction evidence, not a final-source whole-CI pass.

## Windows shard 3: persisted-event observation race

The [completed shard 3 log](evidence/origin-candidate-054/ci/windows-shard3-complete.log) records one failure in `server/index.test.ts`, “parks the turn at the wait ceiling and resumes when the computer frees.” At line 3682, the first `turn.wait_ended` lookup returned `undefined` instead of the expected parked outcome and holder. The preceding start-event assertion had passed. The shard records 1 failed, 5,109 passed and 113 skipped tests; its file summary is 1 failed, 365 passed and 20 skipped, for 386 files.

The [diagnosis receipt](evidence/origin-candidate-054/local/parked-wait-observation-receipt.json) traces the actual order: the server synchronously appends the Parked activity, then publishes `turn.wait_ended`; the event bus queues the NDJSON append asynchronously. The test reads `/messages`, sees the parked activity and immediately takes one disk-backed `/events` snapshot before that queued append completes. This was a persisted-file observation race, not an SSE subscriber. The actual CI RED and traced ordering identify the invalid immediate-snapshot assumption; no application runtime change is required by this repair.

The test adds a bounded five-second poll of the same actual persisted-events endpoint for `turn.wait_ended` before taking the asserted snapshot. It retains holder/resource, parked outcome, elapsed-time, parked-state and resume assertions, the existing 75-second test deadline and owned cleanup; no unconditional sleep or weakened assertion was added. The [focused run](evidence/origin-candidate-054/local/parked-wait-focused.log) passed the three affected wait/park/routing cases with 294 others filtered/skipped in 39.83 seconds, and [targeted lint](evidence/origin-candidate-054/local/parked-wait-lint.log) passed. The original CI failure was retained rather than rerun. These are local isolated fixture checks, not a final-source Windows CI pass.
